C++的设计哲学：
明确性：希望你明确指定重要的事情

零开销：不为不需要的功能付出代价

控制权：程序员完全控制初始化过程

重要的事情必须明确指定，编译器不会猜测你的业务需求。



一。纯虚函数接口

定义接口：基类用纯虚函数定义必须的行为

提供默认：用普通虚函数提供可选覆写的通用逻辑

具体实现：子类实现纯虚函数，可覆写普通虚函数

面向接口编程：代码使用基类指针/引用，不依赖具体类型

核心思想：依赖倒置原则 - 高层模块不应该依赖低层模块，二者都应该依赖抽象。抽象不应该依赖细节，细节应该依赖抽象。

这种设计让系统：

✅ 易于扩展：新增机器人类型不影响现有代码

✅ 易于维护：修改具体实现不影响接口

✅ 类型安全：编译器检查实现完整性

✅ 代码复用：通用逻辑在基类中实现


二。枚举类型与宏定义
总结对比表
特性	宏定义 (#define)	枚举 (enum class)
类型安全	❌ 无类型检查	✅ 强类型检查
作用域	❌ 全局污染 	✅ 作用域限定
调试友好	❌ 看到数字值	✅ 看到枚举名
重构安全	❌ 容易出错	    ✅ IDE支持好
类型转换	❌ 隐式转换	    ✅ 需要显式转换
扩展性	⚠️ 需要小心	    ✅ 易于扩展
结论：在现代C++开发中，除非有特殊需求，否则应该总是优先使用 enum class 而不是宏定义。这能提供更好的类型安全、代码可维护性和调试体验。


三。getter方法
Getter的优点总结：
封装性：隐藏实现细节

验证控制：可以在获取时进行验证

计算支持：可以返回计算值而非存储值

调试支持：可以添加日志和监控

兼容性：修改内部实现不影响外部接口

Getter是对象的"安全窗口"，让外部代码能看到内部状态，但不能随意修改，保证了对象的完整性和安全性。

在这个机器人系统中，Getter让RobotManage能查询机器人的状态，同时确保机器人内部数据不会被意外破坏。



四。自定义构造函数
// 构造函数
Robot(uint16_t team_id, uint16_t robot_id, RobotType type)
    : team_id_(team_id),
    robot_id_(robot_id),
    type_(type),
    status_(RobotStatus::kNormal),
    max_hp_(0),
    max_heat_(0),
    current_hp_(0),
    current_heat_(0) {
}
总结：
尽量使用初始化列表：性能更好，支持const/引用成员

初始化顺序：按照成员声明顺序，与初始化列表顺序无关

保持简单：构造函数应该只做初始化，复杂的逻辑放到其他函数

提供合理的默认值：如 status_(RobotStatus::kNormal)

考虑异常安全：如果可能抛出异常，要小心资源泄漏

构造函数一次性、高效地初始化了所有成员变量，使用C++的初始化列表语法，避免了不必要的默认构造和后续赋值，是标准的C++构造函数写法。


五。静态方法
// 静态方法：根据等级获取血量
static uint16_t GetHpForLevel(InfantryLevel level) {
    switch (level) {
    case InfantryLevel::kLevel1: return 100;
    case InfantryLevel::kLevel2: return 150;
    case InfantryLevel::kLevel3: return 250;
    default: return 100;
    }
}
静态方法适合：不依赖对象状态的工具函数

switch适合：少量、固定的映射关系

添加default：防御性编程，处理意外输入

对称设计：相关功能放在同一个类中

命名清晰：GetXxxForYyy 明确表示映射关系

这个静态方法是一个设计良好的数据映射工具，将业务逻辑（等级→血量）封装在类内部，提供统一、安全的访问方式，既避免了魔法数字，又方便维护和扩展。


六。 override
override 是C++的"安全检查员"，它确保你真的是在重写基类的虚函数，而不是意外创建了新函数或写错了签名。这是一个必须养成的好习惯，能避免许多难以发现的bug。


七。using namespace std的禁用
Google C++风格指南：
❌ 禁止在头文件中使用 using namespace

❌ 禁止在全局作用域使用 using namespace std

✅ 允许在函数内部、源文件内部有限使用

✅ 允许 using 特定的类型/函数

可读性优先：代码是给人看的，其次才是给机器执行的

一致性：整个项目使用统一的编码风格

简洁性：避免复杂的语言特性

实用性：选择经过验证的最佳实践

可维护性：方便他人理解和修改代码



八。shared_ptr 

总结：为什么要用 shared_ptr？
方面	    普通指针 (Robot*)	   智能指针 (shared_ptr<Robot>)
内存管理	     手动new/delete	         自动管理
多所有者	     容易出错	             引用计数安全支持
异常安全	     可能泄漏	             自动清理
性能	     无额外开销	            有引用计数开销
代码安全性	低（容易出错）	        高（编译器帮助）
适合场景   	简单、局部使用	         复杂所有权关系

shared_ptr 提供了自动的、安全的、共享的所有权管理，特别适合对象需要在多个地方共享、生命周期复杂的场景。


九。std::vector<std::shared_ptr<Robot>>Base

多态容器（Polymorphic Container）；基于智能指针的对象池

适用场景：

需要存储派生类对象的集合

对象需要在多个地方共享

对象的生命周期复杂

需要支持运行时多态

这个存储池的核心原理是：

  间接存储：vector存储的是指针，不是对象本身

  引用计数：shared_ptr通过计数跟踪对象被引用的次数

  自动清理：当引用计数归零时，自动删除对象

  共享所有权：多个容器可以安全地共享同一个对象

本质上是：将内存管理的责任从程序员转移给智能指针，通过引用计数机制实现自动的、安全的内存管理，同时保持对多态对象的支持。

这种设计特别适合需要复杂对象生命周期管理和多容器共享对象的场景，比如游戏中的实体管理系统、GUI系统中的控件管理等。
